# 审计方法论（severity / confidence / 污点追踪）

本文是 SKILL.md §1 的展开，供所有模块共同遵循。

## 1. 最顶级污点源（Top-level Taint Source）

"追到最顶级污点源"指：污点数据**首次进入程序边界**的位置，而不是它在业务函数里被第一次使用的位置。

合格的 `source.location` 示例：
- HTTP handler 的 `req.query` / `req.body` / `req.params` / header（Express、Koa、Gin、Spring `@RequestParam` 等）
- 消息队列消费者的回调入参（Kafka / RabbitMQ / SQS consumer）
- 定时任务读取的外部数据（拉取第三方 API、解析上传目录文件）
- 从数据库读出、且该字段历史上由用户写入的值（二阶注入场景）
- 文件上传的文件名、MIME、内容

不合格的 `source.location`：
- 某个内部工具函数的参数（除非该函数本身是 RPC/CLI 入口）
- service 层方法的入参（应继续向上追到路由/消费者）

若数据在到达入口前已被框架强制约束（如路由参数被正则限定为 `\d+`），应在
`exploit_conditions` 中说明约束并据此校准 confidence。

## 2. 严重性定级边界案例

| 场景 | 定级 | 理由 |
| --- | --- | --- |
| 公开接口 SQL 注入，可直接 UNION 读任意表 | CRITICAL | 无前置条件的数据泄露 |
| 需登录的 SSRF，可打云元数据端点拿临时凭据 | CRITICAL | 认证后一步到位接管 |
| 需登录的 SSRF，仅能探测内网端口 | HIGH | 本地网络可利用、影响显著 |
| IDOR 读取他人 email/phone | HIGH | 跨用户数据泄露，条件仅"登录" |
| IDOR 读取他人昵称 | MEDIUM | 影响一般 |
| 管理后台 debug 接口暴露，但已挂在内网 SSO 之后 | MEDIUM | 需特定网络位置 |
| 存储型 XSS 打到管理员会话 | HIGH | 需受害者访问，但影响显著 |

原则：先问"攻击者最少需要什么前提、拿到什么"，再对照 SKILL.md §1.3 表格；
前提越多、收益越小，级别越低；拿不准时降半级并写清理由。

## 3. 置信度校准

| 情形 | 建议区间 |
| --- | --- |
| 已在本地推演出完整 payload 且无阻断点 | 0.9–1.0 |
| 漏洞模式明确、已知利用面，但未实际构造 payload | 0.8–0.9 |
| 依赖特定运行时行为（框架版本、DB 方言、配置默认值） | 0.7–0.8 |
| 需要两个以上低概率条件叠加 | 不报告 |

校准锚点：`evidence` 里必须能直接看出 source→sink 的通路。看不出来还想报，
说明证据不足——回代码里补链路，补不出来就不报。

## 4. 污点传播与"净化识别"

追踪时逐跳回答三个问题，任何一问为"否"即中断该链路（或转低置信度）：

1. **赋值/传参是否保义**：字符串拼接、模板插值、数组/对象赋值都保义；
   序列化后再反序列化同样保义。
2. **是否经过有效净化**：
   - 参数化查询 / 预编译语句（SQL：绑定变量是真净化，字符串拼 SQL 不是）
   - 输出编码按上下文（HTML body / 属性 / JS / URL 各不同；`escapeHtml` 用在 JS 上下文不算净化）
   - 路径规范化后做前缀校验（`realpath` 后 `startsWith(allowedDir)` 是真净化；先 `startsWith` 再拼接是假净化）
   - 白名单映射（`{date: "created_at"}` 查表）是真净化；黑名单过滤通常不是
3. **sink 语义是否危险**：ORM 的查询构造器通常自动转义（但 `raw`/`literal` 除外）；
   `child_process.exec` 危险而 `execFile` 参数数组不经过 shell；HTTP 客户端对
   `file://`、`gopher://` 的支持情况需确认。

净化代码与漏洞代码不在同一文件时，必须显式检查净化函数的调用点覆盖
（中间件是全局还是仅部分路由；工具函数是否被该调用方真正使用）。

## 5. 权限边界检查法

对每个携带"资源标识"的已认证入口，依次核对：

1. 标识来自 `req.params` / body（用户可控），还是直接取自认证主体（`req.user.id`）？
2. 取到对象后，是否校验 `object.owner == subject`（或租户一致）？
3. 写操作是否校验角色/权限点，而非仅校验登录？
4. 越权失败路径是否真的拒绝（而不是记日志后继续）？

任何一步缺失且能触达他人资源，即候选 `idor` / `horizontal_authz` / `vertical_authz` /
`tenant_isolation`。
