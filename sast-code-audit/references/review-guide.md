# 模块四复查指南

模块四是误报的最后闸门。对每条发现执行以下流程，再决定终态。

## 1. 复查五步法

1. **重走污点链**：打开 `data_flow` 里每个位置，确认传播真实存在、方向正确、
   中间没有被清单外的净化（重点：同一文件里模块二没细看的 guard 分支）。
2. **确认 source 可控**：`source.location` 是否真在最顶级污点源？数据在入口处
   有没有被框架/中间件约束（路由正则、全局校验层、反代改写）？
3. **确认 sink 语义**：读 sink 处调用的库的实际行为——ORM raw 与构造器的差异、
   `exec` 与 `execFile` 的差异、HTTP 客户端支持的协议。查证时以依赖版本为准，
   不凭记忆。
4. **确认可达性**：路由/命令/消费者真的注册并暴露？鉴权中间件是否覆盖该路由
   （注意路由注册顺序、方法级差异、静态文件前缀）？
5. **确认利用条件**：`exploit_conditions` 逐条成立？需要的角色/网络位置/ payload
   约束是否现实？多个低概率条件叠加 → 降级或判误报。

## 2. 各类型必检误报模式

| 类型 | 高频误报模式 | 复查动作 |
| --- | --- | --- |
| SQL/命令/模板注入 | 净化函数在下游/包装层，模块二没追到 | 沿调用链找 wrapper（`db.raw` 是否经自研封装统一过滤） |
| SSRF | URL 经过 https+域名白名单封装 | 定位封装实现并确认该调用点确经封装、白名单覆盖内网地址段 |
| 路径遍历 | 上传名被重命名；`realpath`+前缀校验存在 | 确认校验发生在拼接**之后**、且失败即拒绝 |
| 文件上传 | 落盘名随机化、扩展白名单、存储与 Web 根隔离 | 确认三个环节同时成立 |
| 反序列化 | 数据源实际是服务端自产+签名 | 确认签名校验与密钥管理 |
| XXE | 解析器已禁用外部实体/框架默认安全 | 查依赖版本的实际默认值 |
| 认证/授权边界 | 全局中间件已覆盖该路由；对象归属在 repository 层过滤 | 逐路由核对注册顺序与中间件挂载点 |
| IDOR/越权 | 对象 id 取自 token 而非用户输入；多租户过滤在 query 层 | 核对 `req.user` 来源与查询构造 |
| 密码重置/令牌 | 高熵+一次性+时效三要素齐全 | 核对生成、存储、校验三处代码 |
| 存储型 XSS | 输出侧按上下文编码；富文本经白名单净化 | 同时核对输入侧与渲染侧 |

## 3. 终态判定与输出要求

- **confirmed**：五步全部通过且无需修改。可选附 `review_note` 记录核查点。
- **updated**：链路成立但定级/置信度/利用条件/修复建议需要修正。
  `name` 前缀 `【复查更新】-`，`review_note` 写明"改了什么、依据是什么"。
- **false_positive**：链路断裂（不可控 source / 假 sink / 不可达 / 已被净化）。
  `name` 前缀 `【复查认定误报】-`，`review_note` 写明**证据链断在哪一跳**。
- 复查中发现原发现描述混杂多个问题时：原条目按主问题定终态，必要时**拆分**新条目
  （继续编 id，`origin_stage=4`，`review_status=confirmed`，`review_note` 注明拆分来源）。
- 禁止行为：未经五步复查直接 confirmed；为降误报率把"难验证"草率判为误报；
  修改 id 或 fingerprint（fingerprint 必须仍等于字段拼接结果）。
